# 竞赛展示视频脚本(5 分钟)—— ylong_http_client HTTPS 代理支持

> 风格:口语化、节奏紧凑。总时长严格控制在 5:00 内。所有命令均为本仓库真实可运行命令。
> 通用前置(录制前先设好,画面不必展示):
> `export OPENSSL_DIR=<prefix> LD_LIBRARY_PATH=<prefix>/lib RUSTFLAGS="-L <prefix>/lib -l ssl -l crypto"`
> `<prefix>` 为本机 OpenSSL 前缀(如 `/usr`);RISC-V 板上用 `OPENSSL_LIB_DIR=/usr/lib/riscv64-linux-gnu OPENSSL_INCLUDE_DIR=/usr/include`。

| **0:55–1:40** | S3 终端运行:<br>`cargo test --no-default-features --features async,http1_1,tokio_base,tls_default --test sdv_async_https_proxy`<br>结果滚动显示 6 例 ok(镜头停在 mTLS 两例) | 先看功能。这是 tokio 上的 6 个端到端集成测试:TLS-in-TLS 成功、407 拒绝、不受信代理证书被拒、凭据只在 TLS 内、以及双向认证 mTLS 的成功与缺证书被拒。注意 mTLS——原来这个库连设置客户端私钥的接口都没有,我们补齐了底层 OpenSSL FFI,双向认证才真正跑通。 |
| **1:40–2:10** | S4 终端运行:<br>`cargo test --no-default-features --features async,http1_1,http2,ylong_base,tls_default --test sdv_async_https_proxy_ylong`<br>显示 1 例 ok | 赛题要求异步 TLS 在 tokio 和 ylong_runtime 两种运行时上都正常。这是切换到 ylong_runtime 的端到端用例,同样跑通 TLS-in-TLS。两种运行时都覆盖了。 |
| **2:10–2:45** | S5 代码:`async_impl/proxy.rs` 的 `trait TunnelConnect`,再切到 `TlsConfig::builder().private_key_file(..).alpn_protocols(&["h2","http/1.1"])` | 可扩展性靠这个 TunnelConnect trait:明文和 HTTPS 代理都是它的实现,想加 SOCKS 只要再写一个实现加一个分支,连接器一行都不用改。代理的 TLS 配置也很完整——CA、客户端证书加私钥、算法套件、版本范围,还有新公开的 ALPN 列表,而且只作用于代理这一跳。 |
| **2:45–3:25** | S6 终端运行:<br>`cargo bench --no-default-features --features async,http1_1,tokio_base,tls_default --bench https_proxy_bench`<br>镜头停在单连接对库结果与 P50/P90/P99/P99.9 那几行 | 性能我们说实话。单连接、库对库,ylong 大约 4310、libcurl 库大约 4237,差 1.5%,基本持平——因为两端都被同一个 OpenSSL 卡住。我们还输出 P50 到 P99.9 的尾延迟,不只报平均值。 |

| **3:55–4:35** | S8 RISC-V 结果图(截图):K=50…1000 ylong ≈+30%;下方叠复现命令:<br>`BENCH_ROLE=server taskset -c 4-7 <bench-bin>`<br>`BENCH_ROLE=client BENCH_RT=current BENCH_CONCURRENCY=500 BENCH_LIBCURL=both PROXY_ADDR=... ORIGIN_ADDR=... taskset -c 0 <bench-bin>` | 那 20% 的目标呢?顺着根因,我们找到了异步真正的主场:受限 CPU 上承载大量并发连接。客户端钉在单核,ylong 用单线程运行时把上千条连接复用在一个 epoll 上,而 libcurl 最常见的用法是每连接一个线程。RISC-V 真机上,K 从 50 到 1000,ylong 稳定领先大约 30%,两轮都能复现,达成 20% 以上。诚实说明:这是 I/O 调度的胜利,不是加密更快;我们也没有对 curl_multi 下结论,因为它平台太敏感。 |
