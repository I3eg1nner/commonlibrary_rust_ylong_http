# ylong_http_client HTTPS 代理模块 —— 方案设计与实现

## 1. 背景与目标

`ylong_http_client` 原先只支持**明文(HTTP)代理**:当目标是 HTTPS 站点、且经过代理时,
对代理的 `CONNECT` 隧道始终建立在**未加密的 TCP** 之上。这带来两个问题:

- 代理凭据(`Proxy-Authorization`)与 `CONNECT` 元数据在网络上明文暴露;
- 无法用于强制要求 **TLS 代理(HTTPS 代理)** 的环境。

同时,代理逻辑内联在连接器(connector)中,难以扩展新的代理协议;HTTPS 代理路径也从未与
`libcurl` 做过性能对标。

本方案围绕三个子任务展开:

| 子任务 | 内容 |
|--------|------|
| **子任务 1** | 支持 HTTPS 代理:依赖 OpenSSL 实现 TLS;支持代理服务器 TLS **单向/双向**证书验证;支持设置代理相关 TLS 配置(客户端证书、私钥、算法套件等) |
| **子任务 2** | 代理功能模块化:结合已有 tunnel 能力,抽取独立代理模块,并保证新增代理协议的可扩展性 |
| **子任务 3** | 性能提升:与 libcurl 对比,验证 HTTPS 代理场景性能,目标 **提升 20%+** |

## 2. 总体方案设计

### 2.1 核心思路:TLS-in-TLS(嵌套 TLS)

HTTPS 代理场景下,一次请求需要建立**两层** TLS:

```
客户端 ──TLS①──▶ HTTPS 代理 ──(CONNECT 隧道)──▶ 目标服务器
        └────────────────── TLS② (嵌套在 TLS① 内) ──────────────┘
```

1. 先与**代理**完成 TLS 握手(TLS①),使用**代理专属**的 TLS 配置;
2. 在 TLS① 之上发送 `CONNECT host:port`,代理返回 `200` 后隧道建立;
3. 在同一条 TLS① 流之上,再与**目标服务器**完成 TLS 握手(TLS②);
4. 之后的 HTTP 报文跑在 TLS②(它又跑在 TLS① 里)。

### 2.2 关键抽象:`ProxyTunnel` 统一传输层

为了让"目标 TLS 层"无需关心代理这一跳是否加密,引入一个传输枚举 `ProxyTunnel`,
它实现了异步/同步读写 trait,因此目标 TLS 可以**统一地**包裹它:

```rust
// async_impl/proxy.rs
pub enum ProxyTunnel {
    Plain(TcpStream),                       // 直连 / 明文代理隧道
    Tls(Box<AsyncSslStream<TcpStream>>),    // 到 HTTPS 代理的 TLS 会话
}
// impl AsyncRead + AsyncWrite for ProxyTunnel { ... 转发 ... }
```

于是 `MixStream::Https` 由原来的 `AsyncSslStream<TcpStream>` 改为
`AsyncSslStream<ProxyTunnel>`:

- 直连 HTTPS / 明文代理隧道 → `ProxyTunnel::Plain`;
- HTTPS 代理 → `ProxyTunnel::Tls`(即 TLS-in-TLS)。

> 现成条件:`AsyncSslStream<S>`(异步)与 `SslStream<S>`(同步)本就对内层流泛型,
> `Ssl::connect<S>` 也是泛型,因此**嵌套 TLS 在类型层面天然可行**,只需提供一个同时实现
> 读写 trait 的内层传输,即 `ProxyTunnel`。

### 2.3 可扩展抽象:`TunnelConnect`

把"如何在一条到代理的 TCP 上建立通往目标的隧道"抽象成一个 trait,连接器只依赖该抽象:

```rust
// async_impl/proxy.rs
pub(crate) trait TunnelConnect {
    fn tunnel(&self, tcp: TcpStream, host: &str, port: u16, auth: Option<String>)
        -> impl Future<Output = Result<ProxyTunnel, HttpClientError>> + Send;
}

pub(crate) struct HttpProxyTunnel;      // 明文 CONNECT
pub(crate) struct HttpsProxyTunnel {    // 先到代理建 TLS,再在其上 CONNECT
    pub(crate) config: TlsConfig,
    pub(crate) proxy_host: String,
}
```

**新增代理协议(如 SOCKS)= 新增一个 `TunnelConnect` 实现**,连接器代码无需改动。
同步侧 `sync_impl/proxy.rs` 提供镜像结构(基于阻塞 `Read/Write`)。

### 2.4 代理 TLS 配置(单向 / 双向)

代理这一跳的 TLS 配置与**目标服务器**完全独立,挂在 `ProxyInfo` 上:

```rust
// util/proxy.rs
pub(crate) struct ProxyInfo {
    scheme: Scheme,
    authority: Authority,
    basic_auth: Option<HeaderValue>,
    #[cfg(feature = "__tls")]
    proxy_tls: Option<TlsConfig>,   // 代理专属 TLS 配置
}

impl ProxyInfo {
    fn is_tls(&self) -> bool { self.scheme == Scheme::HTTPS || self.proxy_tls.is_some() }
}
```

- **单向验证**:用代理 `TlsConfig` 设置受信 CA(`ca_file` / `add_root_certificates`),验证代理证书;
- **双向验证(mTLS)**:用代理 `TlsConfig` 设置**客户端证书 + 私钥**,在代理要求时出示;
- 协议版本、算法套件、SNI、accept-invalid 等同样作用于代理这一跳,且不影响目标连接。

## 3. 实现细节

### 3.1 连接器改造(async / sync 对称)

连接器在选中代理后计算一个 `ProxyKind`,再委派给代理模块:

```rust
enum ProxyKind { Direct, Http, Https { config: TlsConfig, proxy_host: String } }

// https_connect 内:
let transport: ProxyTunnel = match proxy_kind {
    ProxyKind::Direct          => ProxyTunnel::Plain(tcp),
    ProxyKind::Http            => HttpProxyTunnel.tunnel(tcp, &host, port, auth).await?,
    ProxyKind::Https { .. }    => HttpsProxyTunnel { config, proxy_host }
                                      .tunnel(tcp, &host, port, auth).await?,
};
// 目标 TLS 统一包裹 transport:
let stream = config.ssl_new(&host)
    .and_then(|ssl| AsyncSslStream::new(ssl.into_inner(), transport, pinned_key))?;
```

`HttpsProxyTunnel::tunnel` 的步骤:**到代理建 TLS → 在 TLS 上 `connect_tunnel`(CONNECT)→ 返回 `ProxyTunnel::Tls`**。
`connect_tunnel` 对底层流泛型(`S: AsyncRead + AsyncWrite`),因此明文/加密两种隧道复用同一段逻辑;
非 `200`(如 `407`)被映射为 `Connect` 类错误并**跳过目标握手**。

### 3.2 连接建立完整流程

```
client.request(uri)
   └─ connector.connect(uri)
        ├─ proxies.match_proxy(uri) → 选代理、算 ProxyKind、取 basic_auth
        ├─ Scheme::HTTP  → 直接到代理发请求(明文,不隧道)
        └─ Scheme::HTTPS → DNS → TCP → https_connect:
              ├─ ProxyKind::Https → ① 到代理 TLS 握手  ② CONNECT(凭据在 TLS 内)  ③ 200
              ├─ 在 ProxyTunnel 之上做 ④ 目标 TLS 握手(嵌套)
              └─ 返回 MixStream::Https(AsyncSslStream<ProxyTunnel>)
```

### 3.3 公共 API

```rust
// 代理专属 TLS(独立于目标 TLS)
let proxy_tls = TlsConfig::builder()
    .ca_file("proxy_ca.pem")                                  // 单向:信任代理 CA
    .certificate_file("client.pem", TlsFileType::PEM)         // 双向:客户端证书
    .private_key_file("client.key", TlsFileType::PEM)         // 双向:客户端私钥(新增)
    .min_proto_version(TlsVersion::TLS_1_2)                   // 协议版本
    .cipher_list("...")                                        // 算法套件
    .build()?;

let client = ClientBuilder::new()
    .proxy(Proxy::all("https://proxy.example.com:8443")       // https:// ⇒ 代理走 TLS
        .basic_auth("user", "pass")
        .tls_config(proxy_tls)                                // 新增的 additive 方法
        .build()?)
    .build()?;
```

> 设计取舍:不在 `ProxyBuilder` 上重复整套 TLS builder,而是复用成熟的
> `TlsConfig::builder()`,通过单一入口 `ProxyBuilder::tls_config(TlsConfig)` 接入代理作用域。

### 3.4 性能方案

- 复用既有**连接池(keep-alive)**:代理 TLS 握手在同一条隧道上被多次请求摊销;
- 新增基准 `benches/https_proxy_bench.rs`:同一套 TLS 代理 + TLS 源服务器下,顺序、keep-alive、
  固定负载,分别测 `ylong_http_client` 与系统 `curl`(强制 `--http1.1` 对齐),输出吞吐对比。

## 5. 遇到的困难与解决

### 困难 1:`MixStream::Https` 硬编码 `TcpStream`,无法承载嵌套 TLS
**问题**:目标 TLS 流类型写死为 `AsyncSslStream<TcpStream>`,而 HTTPS 代理需要让目标 TLS
包裹"到代理的 TLS 流"。
**解决**:引入 `ProxyTunnel`(`Plain` / `Tls` 两态,实现读写 trait),把 `MixStream::Https`
统一改为 `AsyncSslStream<ProxyTunnel>`。由于 SSL 流本就对内层泛型,改动很小且对直连/明文代理路径透明。

### 困难 2:双向验证(mTLS)缺少"设置私钥"的能力 —— 子任务 1 的硬伤
**问题**:`TlsConfigBuilder` 只能加载客户端**证书**(`certificate_file`),却**没有任何设置私钥**的方法;
没有私钥就无法完成 mTLS,等于子任务 1 的"双向证书验证 / 客户端私钥"无法真正达成。最初用
`tls_config(TlsConfig)` 的方案在 mTLS 上是走不通的。
**解决**:补齐整条链路 —— FFI 绑定 `SSL_CTX_use_PrivateKey_file` + `SSL_CTX_check_private_key`
(加载后校验私钥与证书匹配)→ `SslContextBuilder::set_private_key_file` → 公共
`TlsConfigBuilder::private_key_file`。随后用"代理强制要求客户端证书"的集成测试验证通过。

### 困难 3:`sync_impl` 历史性编译损坏,同步路径根本无法构建
**问题**:仓库基线状态下,只要启用 `sync`,编译就失败(用 `git stash` 在基线确认),原因是多处:
- `sync_impl/client.rs` 构造 `ConnectorConfig` 时缺 `timeout` 字段;
- `sync_impl/pool.rs` 调用 `Pool::get` 的参数个数/闭包签名与现版本不符;
- 共享模块 `util/interceptor/mod.rs` 无条件 `use crate::async_impl::{...}`,在纯 sync 下找不到;
- `lib.rs` 的 `runtime` 仅在 `tokio_base + async` 下导出 `Semaphore/sleep/Sleep`,而 sync 用到的
  共享 dispatcher / rate-limiter 也需要它们。

**解决**:逐项修复 —— 补 `ConnectorConfig` 字段;对齐 `Pool::get`/`Conns::new` 签名;把 interceptor
里 async 专用的导入与方法用 `#[cfg(feature = "async")]` 门控;把 `Semaphore/sleep/Sleep` 改为在
`tokio_base` 下即导出。修复后同步 HTTPS 代理路径可端到端编译并通过集成测试,且不影响 async。

### 困难 4:no-tls 构建因 `libc` 门控错误而失败
**问题**:`async_impl/connector/mod.rs` 与 `dns/happy_eyeballs.rs` 中 `use libc::{gid_t, uid_t}`
仅按 `target_os = "linux"` 门控,但 `libc` 只在 TLS 相关 feature 下才是依赖,导致 Linux 下 no-tls 构建失败。
**解决**:把这两处 `use libc` 的门控收紧为与其唯一使用点一致的
`#[cfg(all(target_os = "linux", feature = "ylong_base", feature = "__tls"))]`。之后 async/sync ×
tls 开关的所有组合均可编译。

### 困难 5:测试环境的 OpenSSL 链接与 feature 组合
**问题**:`cargo check` 可过,但 `cargo test`/`bench` 因 dev 依赖 `tokio-openssl`(经 `openssl-sys`)
找不到 OpenSSL 而失败;自研 FFI 还需链接 `libssl/libcrypto`;`sync` 又需配合具体 runtime 组合。
**解决**:用 `OPENSSL_DIR=<prefix>` 提供 dev 依赖所需路径,并以
`RUSTFLAGS="-L <prefix>/lib -l ssl -l crypto"` 让自研 FFI 正确链接;明确可用组合
(`async,http1_1,tokio_base,tls_default`、`sync,http1_1,tls_default,tokio_base` 等)。

### 困难 6:性能对比的公平性
**问题**:与 `curl` CLI 对比存在进程启动开销;若 curl 走 HTTP/2 而 ylong 走 HTTP/1.1 则不对等。
**解决**:让单个 curl 进程**复用一条隧道**承载全部请求(摊销启动开销),并强制 `--http1.1`
与 ylong 对齐;源服务器也仅开 HTTP/1.1。最终对比中 ylong 还**额外校验了代理证书**(curl 跳过),
属于对 ylong 不利的保守口径。

## 6. 性能结果与结论(如实)

**关键:必须区分两种 libcurl 口径**(子任务要求的是「与 libcurl **库**」):
- **libcurl 库**:用 `curl` crate 同进程复用 `Easy` 句柄直接调库 —— 真正的库对库对比;
- **`curl` 命令行**:调用 curl 工具,含 CLI 进程/参数开销,**不是库的对比**,会高估 ylong。

RISC-V 真机(SpacemiT K3,8 核,系统 OpenSSL 3.5,两端同库;2000 请求/200 预热/1KB/keep-alive/HTTP-1.1),
5 轮中位:

| 对比口径 | ylong | 对方 | 提升 |
|----------|-------|------|------|
| **vs libcurl 库**(主口径) | ~4,310 req/s | ~4,237 req/s | **≈ +1.5%**(+0.6%…+2.2%) |
| vs `curl` CLI(仅参考) | ~4,310 req/s | ~3,210 req/s | +26%(含 CLI 开销) |

**结论(如实):**
- 与 **libcurl 库**对比,ylong **基本持平、略快约 1–2%**,**未达到子任务 3 的「提升 20%+」目标**;
  二者都在同一条 TLS-in-TLS 路径上受 OpenSSL 制约,出现大幅差距不符合预期,能与成熟 C 库打平已是良好结果。
- 早先的 **+26%/+41.5% 是对 `curl` CLI 工具**测得,几乎全为 CLI 开销,不代表库的性能优势,已在文档中改为仅作参考。
- 若要冲击 20% 目标,需做针对性优化(tasks 6.4:隧道缓冲复用、CONNECT 批量写、消除层间拷贝),
  但在 OpenSSL 受限路径上对成熟 C 库提升 20% 难度较大。

> 复现脚本与原始数据见 `openspec/changes/https-proxy-module/benchmark-results.md` 与
> `docs/https-proxy/02-架构与接口测试.md` 第五节。
