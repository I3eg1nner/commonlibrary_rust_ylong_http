## 1. 背景与问题

`ylong_http_client` 原先只支持**明文(HTTP)代理**:当目标是 HTTPS 站点且经过代理时,对代理的 `CONNECT` 隧道始终建立在**未加密的 TCP** 之上。这带来两类问题:

- **安全**:代理凭据(`Proxy-Authorization`)与 `CONNECT` 元数据在网络上明文暴露,无法用于强制 TLS 代理的企业/受控环境;
- **可维护**:代理逻辑内联在连接器(connector)中,难以扩展新的代理协议;HTTPS 代理路径也从未与 `libcurl` 做过性能对标。

竞赛赛题据此拆为三个子任务:

| 子任务 | 内容 | 权重侧重 |
|--------|------|---------|
| **子任务 1** | 支持 HTTPS 代理:基于 OpenSSL 实现 TLS;支持代理服务器 TLS **单向/双向**证书验证;支持代理相关 TLS 配置(客户端证书、私钥、算法套件等) | 任务完成度 / 技术先进性 |
| **子任务 2** | 代理功能**模块化**:结合已有 tunnel 能力抽取独立代理模块,保证新增代理协议的可扩展性 | 技术先进性 |
| **子任务 3** | **性能提升**:与 libcurl 对比,验证 HTTPS 代理场景性能,目标提升 **≥20%** | 性能指标 |

---

## 2. 目标与范围(含例外)

**目标(Goals):**

- 支持 TLS 代理:到代理建立 TLS、在其上发 `CONNECT`、再在隧道内对目标做嵌套 TLS(TLS-in-TLS);
- 代理这一跳拥有**独立**的 TLS 配置(CA、客户端证书+私钥、协议版本范围、算法套件、SNI、主机名校验、ALPN),支持单向与双向验证;
- 将代理逻辑抽取为**独立、可扩展**模块,新增代理协议(如 SOCKS)无需改动连接器;
- 提供可复现的 HTTPS 代理基准,与 libcurl 对比并如实认证 ≥20% 目标。

**明确不做(Non-Goals / 例外):**

- 不实现 SOCKS 等新协议本体(只让抽象**支持**扩展);
- 不做代理自动发现(PAC/WPAD)、系统代理探测、代理链;
- 不改变目标服务器 TLS 行为与其公共 TLS 语义;
- **HTTP/3 与同步(sync)HTTPS 代理不在赛题范围**(赛题聚焦异步 TLS 读写在 tokio 与 ylong_runtime 上正常);原有接口不受影响,两个必需构建组合均干净编译。

## 3. 总体架构

代理能力按**职责单一**拆成三层,`★` 为本次新增/重点改动位置:

```
            ┌─────────────────────────────────────────────────────────┐
   选择层    │ util/proxy.rs                                            │
 (协议无关)  │   Proxies::match_proxy(uri) → 按 scheme / no_proxy 选代理 │
            │   ProxyInfo{ scheme, authority, basic_auth, proxy_tls★ } │
            └───────────────────────────┬─────────────────────────────┘
                                        │ ProxyKind(Direct/Http/Https)
            ┌───────────────────────────▼─────────────────────────────┐
   隧道层★   │ async_impl/proxy.rs · sync_impl/proxy.rs                 │
 (可扩展)    │   trait TunnelConnect { fn tunnel(..) -> ProxyTunnel }   │
            │   HttpProxyTunnel  : 明文 CONNECT                         │
            │   HttpsProxyTunnel : 先到代理建 TLS,再在其上 CONNECT     │
            │   ProxyTunnel = Plain(TCP) | Tls(到代理的 TLS 流)        │
            │   connect_tunnel<S>(..)  ← 明文/加密隧道复用同一段逻辑    │
            └───────────────────────────┬─────────────────────────────┘
                                        │ ProxyTunnel
            ┌───────────────────────────▼─────────────────────────────┐
   连接层    │ async_impl/connector · sync_impl/connector              │
            │   在 ProxyTunnel 之上做「目标服务器 TLS 握手」           │
            │   产出 MixStream::Https(AsyncSslStream<ProxyTunnel>)     │
            └─────────────────────────────────────────────────────────┘
```

**关键设计点:**

- **选择层**与协议无关,HTTP / HTTPS 代理共用一套 scheme 匹配 / no_proxy / basic_auth 逻辑;
- **隧道层**是唯一扩展点:`TunnelConnect` 抽象了「在到代理的连接上建立通往目标的隧道」;
- **连接层**只认 `ProxyKind` 与 `ProxyTunnel`,对「代理这一跳是否加密」无感知 —— 目标 TLS 永远统一包裹 `ProxyTunnel`,从而天然支持 TLS-in-TLS。

### 3.1 核心思路:TLS-in-TLS(嵌套 TLS)

HTTPS 经 HTTPS 代理时,一次请求要建立**两层** TLS:

```
客户端 ──TLS①──▶ HTTPS 代理 ──(CONNECT 隧道)──▶ 目标服务器
        └────────────────── TLS②(嵌套在 TLS① 内)────────────────┘
```

1. 先与**代理**完成 TLS 握手(TLS①,用**代理专属** TLS 配置);
2. 在 TLS① 之上发送 `CONNECT host:port`,代理返回 `200` 后隧道建立;
3. 在同一条 TLS① 流之上,再与**目标服务器**完成 TLS 握手(TLS②);
4. 之后的 HTTP 报文跑在 TLS②(它又跑在 TLS① 里)。凭据(`Proxy-Authorization`)只在 TLS① 内传输,不再明文暴露。

### 3.2 关键抽象:`ProxyTunnel` 统一传输层

为让「目标 TLS 层」无需关心代理这一跳是否加密,引入传输枚举,它实现异步读写 trait(源码见 `async_impl/proxy.rs`):

```rust
pub enum ProxyTunnel {
    Plain(TcpStream),                       // 直连 / 明文代理隧道
    Tls(Box<AsyncSslStream<TcpStream>>),    // 到 HTTPS 代理的 TLS 会话
}
// impl AsyncRead + AsyncWrite for ProxyTunnel { ... 转发到内部流 ... }
```

`MixStream::Https` 由原来的 `AsyncSslStream<TcpStream>` 改为 `AsyncSslStream<ProxyTunnel>`。因 `AsyncSslStream<S>` / `SslStream<S>` 本就对内层流泛型、`Ssl::connect<S>` 也是泛型,**嵌套 TLS 在类型层面天然可行**,改动很小且对直连/明文代理路径透明。

### 3.3 可扩展抽象:`TunnelConnect`

```rust
pub(crate) trait TunnelConnect {
    fn tunnel(&self, tcp: TcpStream, host: &str, port: u16, auth: Option<String>)
        -> impl Future<Output = Result<ProxyTunnel, HttpClientError>> + Send;
}
pub(crate) struct HttpProxyTunnel;                          // 明文 CONNECT
pub(crate) struct HttpsProxyTunnel { config: TlsConfig, proxy_host: String } // 到代理 TLS + CONNECT
```

连接器选中代理后计算一个 `ProxyKind` 并委派:

```rust
enum ProxyKind { Direct, Http, Https { config: TlsConfig, proxy_host: String } }

let transport: ProxyTunnel = match proxy_kind {
    ProxyKind::Direct       => ProxyTunnel::Plain(tcp),
    ProxyKind::Http         => HttpProxyTunnel.tunnel(tcp, &host, port, auth).await?,
    ProxyKind::Https { .. } => HttpsProxyTunnel { config, proxy_host }
                                   .tunnel(tcp, &host, port, auth).await?,
};
let stream = config.ssl_new(&host)
    .and_then(|ssl| AsyncSslStream::new(ssl.into_inner(), transport, pinned_key))?;
```

**新增协议 = 新增一个 `TunnelConnect` 实现 + 在 `ProxyKind` 加一个分支,连接层与选择层不改。** `connect_tunnel<S>` 对底层流泛型,因此明文/加密两种隧道复用同一段 CONNECT 逻辑;非 `200`(如 `407`)被映射为 `Connect` 类错误并**跳过目标握手**。

## 4. 核心技术

### 4.1 OpenSSL c_openssl FFI(无新增第三方依赖)

TLS 能力全部走仓库**自研** OpenSSL FFI(`util/c_openssl/`),不引入新的 TLS crate;受 `__tls` / `__c_openssl` feature 门控。明文代理选择逻辑在无 TLS 时仍可用。

### 4.2 单向与双向证书验证

代理这一跳的 TLS 配置挂在 `ProxyInfo.proxy_tls` 上,与目标服务器完全独立:

- **单向验证**:用代理 `TlsConfig` 设受信 CA(`ca_file` / `add_root_certificates`),验证代理证书;
- **双向验证(mTLS)**:用代理 `TlsConfig` 设**客户端证书 + 私钥**,在代理要求时出示。

> **子任务 1 的硬伤与补齐**:原 `TlsConfigBuilder` 只能加载客户端**证书**(`certificate_file`),**没有任何设置私钥的方法** —— 没有私钥就无法完成 mTLS。本次补齐整条链路:FFI 绑定 `SSL_CTX_use_PrivateKey_file` + `SSL_CTX_check_private_key`(加载后校验私钥与证书匹配)→ `SslContextBuilder::set_private_key_file` → 公共 `TlsConfigBuilder::private_key_file`。由 mTLS 集成测试验证通过。

### 4.3 完整代理 TLS 配置(含 ALPN)

复用成熟的 `TlsConfig::builder()`,通过单一入口 `ProxyBuilder::tls_config(TlsConfig)` 接入代理作用域(additive,不破坏既有 API):

```rust
let proxy_tls = TlsConfig::builder()
    .ca_file("proxy_ca.pem")                             // 单向:信任代理 CA
    .certificate_file("client.pem", TlsFileType::PEM)    // 双向:客户端证书
    .private_key_file("client.key", TlsFileType::PEM)    // 双向:客户端私钥(★ 新增)
    .min_proto_version(TlsVersion::TLS_1_2)              // 协议版本范围
    .cipher_list("...")                                   // 算法套件
    .alpn_protocols(&["h2", "http/1.1"])                  // ALPN 协议列表(★ 转为公开 API)
    .build()?;

let client = ClientBuilder::new()
    .proxy(Proxy::all("https://proxy.example.com:8443")   // https:// ⇒ 代理走 TLS
        .basic_auth("user", "pass")
        .tls_config(proxy_tls)
        .build()?)
    .build()?;
```

上述所有项(版本范围、算法套件、ALPN、SNI、accept-invalid 等)**仅作用于代理这一跳**,不影响目标连接。ALPN 由内部方法转为公开 `alpn_protocols(&[..])`(源码 `util/c_openssl/adapter.rs`,基于 `SSL_CTX_set_alpn_protos`)。

### 4.4 会话复用(连接池 keep-alive)

复用既有连接池(按代理地址为键),代理 TLS 握手在同一条隧道上被多次请求摊销,无需新增代码。另实现了 TLS 会话恢复(per-`SSL_CTX` session cache,对 pinned/自定义验证器安全关闭),对「长生命周期客户端、反复冷连接同一主机」有效。

## 6. 性能评测(如实)

> **诚实框架**:必须区分「libcurl **库**」(`curl` crate 同进程复用 `Easy` 句柄 —— 真正的库对库)与「`curl` **命令行**」(含 CLI 进程/参数开销,会高估 ylong)。赛题要求的是与 libcurl **库**对比。硬件为 RISC-V 真机 SpacemiT K3(riscv64gc,8 核,系统 OpenSSL 3.5,libcurl 8.18;ylong 与 curl 链接同一份 OpenSSL,保证公平)。

### 6.1 单连接:与 libcurl 库**持平**

单连接顺序(2000 请求 / 200 预热 / 1KB / keep-alive / 复用一条连接 / HTTP-1.1),RISC-V 5 轮中位:

| 对比口径 | ylong | 对方 | 提升 |
|---|---|---|---|
| **vs libcurl 库(主口径)** | ~4,310 req/s | ~4,237 req/s | **≈ +1.5%**(+0.6%…+2.2%,持平) |
| vs `curl` CLI(仅参考) | ~4,310 req/s | ~3,210 req/s | +26%(含 CLI 开销,非库对比) |

单请求延迟:ylong ≈ 0.23 ms,libcurl 库 ≈ 0.24 ms,curl CLI ≈ 0.31 ms。**单连接口径下「≥20% 对库」未达成,公平结果是持平** —— 两端同受 OpenSSL 制约。

### 6.2 perf 根因(为何单连接必然持平)

对 256KB 大报文用 `perf` 剖析(源在独立进程):

- **同密码套件**:两端都协商 `ECDHE-RSA-CHACHA20-POLY1305`,`EVP_DecryptUpdate`(ChaCha20)占比相同(~5.7%),排除加密差异;
- **指令数几乎相同**:ylong 21.31B vs libcurl 21.12B;
- **唯一差异是上下文切换**:ylong **110,794** vs libcurl **3,407**(≈33×)→ ylong IPC 偏低(1.27 vs 1.42)、CPU 时间 +18%。

机制:ylong 的**多线程**异步运行时每次 socket 就绪 `Poll::Pending` 都做一次**跨线程调度唤醒**(`ssl_stream/wrapper.rs`→`bio.rs`→`SSL_read` WANT_READ),**嵌套 TLS-in-TLS 再翻倍**;libcurl 单线程阻塞 `read()` 几乎为 0。**改用单线程运行时(`BENCH_RT=current`)后切换数塌缩到 4,328(≈libcurl),根因确认。** 该开销仅在 CPU 饱和时影响壁钟;空闲核下 ylong 仍持平。

> 早先的 **−35%(大报文)/ −14%(并发)/ +26%(K=8)/ +41.5%(x86)** 均为**同机 CPU 竞争 / 共调度 / curl-CLI 口径假象,已全部撤回。**

### 6.3 ≥20% 达成场景:受限 CPU + 高并发(RISC-V 实测)

根因指明了异步真正的优势场景 —— **少线程多路复用海量连接**,并已实测验证:

- **场景(极常见部署)**:受限 CPU 主机(1 vCPU 容器 / sidecar / 边缘盒子)承载大量并发 keep-alive HTTPS 代理连接;
- **ylong**:**单线程运行时**把 K 条连接作为协作式 task 复用在一个 epoll 反应堆(无跨线程唤醒);
- **libcurl 最主流用法**:阻塞 `Easy` API 要并发只能**每连接一个 OS 线程**(K 线程,各持一个 keep-alive 句柄),受限 CPU 上超额订阅核心 → 调度抖动 + K 份驻留栈。

方法:进程隔离(fixtures 钉核 4–7,客户端 `taskset` 钉**单核**核 0),10000 请求、1KB、keep-alive、HTTP/1.1、两端同样 root-ca 验证证书。聚合吞吐,连续两轮:

| 并发 K | ylong(单线程) | libcurl(threads) | Δ 第1轮 | Δ 第2轮 |
|---|---|---|---|---|
| 1(单连接) | ~4,030 | ~3,950 | +2.0% | 持平 |
| 50 | 9,543 / 9,372 | 6,653 / 6,667 | **+30.3%** | **+28.9%** |
| 200 | 7,943 / 7,974 | 5,484 / 5,490 | **+31.0%** | **+31.2%** |
| 500 | 7,339 / 7,323 | 5,108 / 5,025 | **+30.4%** | **+31.4%** |
| 1000 | 6,442 / 6,474 | 4,481 / 4,517 | **+30.4%** | **+30.2%** |

**RISC-V 上 ylong 较 libcurl「每连接一线程」用法稳定领先 ≈+30%(K=50…1000),可复现(轮间差 < 2.5 个百分点),稳过 ≥20%。** x86(128 核、客户端钉单核、20000 请求)同样佐证 +22%…+38%。

### 6.4 对 curl_multi 的诚实界定

- 这是**对 libcurl 最主流并发用法的真实、可复现 ≥20% 优势**,场景常见;
- 它**不是**「数据路径/加密更快」—— 单连接是持平。优势纯来自 **I/O 调度架构**(epoll 多路复用 vs 每连接一线程);
- **未对 `curl_multi`(libcurl 自带单线程事件循环)做认证**。基准含指示性 `curl_multi` 驱动(`BENCH_LIBCURL=multi`),但其数值对平台过于敏感(x86 轮间 ≈2× 抖动、RISC-V 偏低且平),**不主张对 curl_multi 的优势**;严谨对比需 `curl_multi_socket_action`+epoll(届时预期接近持平);
- **达成条件**:(a) ylong 用单线程运行时;(b) CPU 受限(连接数 ≫ 核数)。核多空闲时优势收敛到持平。

### 6.5 度量与方法学

评测采用**两套互补的基准**,分别服务于「对比」与「统计严谨性」两个目的:

1. **自研对比型基准** `benches/https_proxy_bench.rs`(`harness=false`):面向 ylong 与 libcurl 的库对库对比,输出吞吐(RPS)、平均 ms/req、以及 **P50 / P90 / P99 / P99.9** 延迟分位;并有可注入的源端时延旋钮 `BENCH_DELAY_MS` 探测**网络时延维度**(实测:注入 2ms 时延后单连接差距从 −60% 收窄到 −3%,说明差异非数据路径而是调度所致)。旋钮:`BENCH_CONCURRENCY` / `BENCH_RT=current` / `BENCH_LIBCURL=threads\|multi\|both` / `BENCH_ROLE=server\|client`(进程隔离 + taskset)/ `BENCH_DELAY_MS` / `BENCH_PAYLOAD` / `BENCH_REQUESTS`。

2. **criterion 统计型基准** `benches/https_proxy_criterion.rs`:面向单请求时延的**统计严谨测量**,借助 criterion 框架提供**置信区间与离群点检测**,对稳态 keep-alive 的 HTTPS 代理单请求(TLS-in-TLS,全 in-process)给出可靠的时延估计。实测约 **155–169 µs/请求**,与上文单请求 ≈0.23 ms 的量级一致,且为「单连接与 libcurl 持平」这一结论提供了带误差界的支撑。运行命令:

   ```bash
   OPENSSL_DIR=<prefix> LD_LIBRARY_PATH=<prefix>/lib \
   RUSTFLAGS="-L <prefix>/lib -l ssl -l crypto" \
   cargo bench --no-default-features \
     --features async,http1_1,tokio_base,tls_default --bench https_proxy_criterion
   ```

   二者互补:`https_proxy_bench` 负责跨实现/跨场景的对比与分位,`https_proxy_criterion` 负责单点时延的统计置信度。

### 6.6 RISC-V ISA 感知优化:向量 AES 密码优选(平台针对性)

**【已验证】** 单连接持平是在实际协商到的 **TLS 1.2 ChaCha20-Poly1305** 下测得(perf 已证)。但测试板暴露了 **RISC-V 向量密码扩展**——`/proc/cpuinfo` 的 `isa` 串含 `v zvkb zvkg zvkned zvknha zvknhb zvksed zvksh zvkt`(向量 AES `Zvkned` + 向量 GHASH `Zvkg`)。在此硬件上 OpenSSL 3.5 的 AES-GCM 远快于 ChaCha20,即**协商到的恰是对该 CPU 最慢的密码**。

`openssl speed -evp`(16 KB 块):ChaCha20-Poly1305 ≈373 MB/s、**AES-128-GCM ≈2377 MB/s(≈6.4×)**、AES-256-GCM ≈1857 MB/s(≈5.0×)。

端到端 A/B(单连接,两端经 `BENCH_CIPHER` 钉同一密码):

| 负载 | 密码 | ylong req/s | ylong P99(ms) | Δ(换 AES-GCM) |
|---|---|---|---|---|
| 1 KB | ChaCha20 | 4,245 | 0.253 | — |
| 1 KB | **AES-128-GCM** | 4,535 | 0.237 | **+6.8%** |
| 256 KB | ChaCha20 | 219 | 4.72 | — |
| 256 KB | **AES-128-GCM** | 504 | 2.03 | **+130%(2.3×)** |

A/B 干净(仅换 AEAD,同一 harness)。**在该硬件上选 AES-GCM,使 ylong 单连接 HTTPS 代理吞吐在 1 KB 提升 +6.8%、在 256 KB 提升 2.3×,P99 近乎减半**——收益随负载增大,因其受加密制约。

**落地(opt-in、对非 RISC-V 零影响)**:新增 `TlsConfigBuilder::prefer_hardware_aead()`(作用于任意 `TlsConfig`,含代理这一跳)与 `async_impl::ClientBuilder::tls_prefer_hardware_aead()`(作用于**目标/源** TLS——256KB 负载加密就发生在这一跳)。二者通过 `/proc/cpuinfo` 检测 `Zvkned`,存在则对 TLS 1.2 优选 **AES-GCM 密码列表**(TLS 1.3 默认已 AES 优先,无需改)。**【设计】** 检测体以 `#[cfg(all(target_os="linux", target_arch="riscv64"))]` 门控:在其余任何平台该方法编译为**纯空操作**(不读 `/proc/cpuinfo`、不改密码),且为 opt-in——**因此对非 RISC-V 平台性能零影响**。另有 bench 旋钮 `BENCH_CIPHER`(钉服务端密码)与 `BENCH_HW_AEAD=1`(走客户端自动选择,不钉服务端)用于复现。

**【已验证】端到端自动选择**(`BENCH_HW_AEAD=1`,**不钉服务端密码**):客户端自行检测并选中 AES-GCM,达到与「服务端钉 AES」相同的吞吐(256KB 均 504 req/s),证明自动检测生效。此时 **ISA 感知的 ylong 甚至在单连接就超过默认配置的 libcurl**(1KB +8.4%、256KB +39.9%,因默认 libcurl 在该 CPU 仍停在 ChaCha20)。另:`openssl speed` 实测 `OPENSSL_riscvcap=""`(关扩展)AES-GCM 仅 70 MB/s < ChaCha20 373 MB/s,开扩展后 2377 MB/s——即**没有向量 AES 时 AES 反而更慢**,正说明该优化是**硬件条件驱动的**;发行版 OpenSSL 3.5 已启用 RVV crypto,无需重编。

> 诚实界定:对称同密码对比下 libcurl 同样受益(它也走同一 OpenSSL);此优化的价值在于 **ylong 默认就为 RISC-V 选对密码**,而按 x86 式 AES-NI 探测的客户端可能停在 ChaCha20。它是**平台针对性的默认优化**,非「比 libcurl 更快的加密」。

## 8. 可维护性与扩展性:新增 SOCKS 的步骤

1. 在 `async_impl/proxy.rs`(及镜像的 `sync_impl/proxy.rs`)新增 `struct SocksProxyTunnel { .. }`;
2. `impl TunnelConnect for SocksProxyTunnel`,在 `tunnel(..)` 内实现 SOCKS 握手,返回 `ProxyTunnel`;
3. 在连接器的 `ProxyKind` 匹配加一个 `Socks` 分支委派到它;
4. 选择层、连接层的目标 TLS 包裹逻辑**完全不动**。

即:**加协议 = 加一个 trait 实现 + 一个枚举分支**,零侵入。
