# ylong_http 架构、代理功能定位与接口测试文档

## 一、ylong_http 整体架构

`ylong_http` 是一个 Rust 实现的 HTTP 协议栈 + 客户端,采用 workspace 组织,分为两个 crate:

```
commonlibrary_rust_ylong_http/
├── ylong_http/            # 协议层:HTTP 报文的编解码与类型
└── ylong_http_client/     # 客户端层:连接、TLS、代理、连接池、DNS、请求/响应驱动
```

### 1.1 `ylong_http`(协议层)

| 模块 | 职责 |
|------|------|
| `h1/` | HTTP/1.1 编解码 |
| `h2/` | HTTP/2 编解码 + HPACK |
| `h3/` | HTTP/3 编解码 + QPACK |
| `body/` | 报文体类型(Empty/Text/MIME 等),含 `async_impl` / `sync_impl` 两套 `Body` trait |
| `request/`、`response/` | 请求/响应类型与 `RequestBuilder` |
| `headers.rs`、`request/uri/` | 头部与 URI(`Scheme`/`Authority`/`Host`/`Port`) |

协议层不关心 I/O 与 TLS,只负责"字节 ↔ 结构"的转换。

### 1.2 `ylong_http_client`(客户端层)

```
ylong_http_client/src/
├── async_impl/                 # 异步客户端
│   ├── client.rs               #   Client / ClientBuilder
│   ├── connector/mod.rs        #   Connector trait + HttpConnector(连接建立)
│   ├── proxy.rs                #   ★ 异步代理模块:ProxyTunnel / TunnelConnect
│   ├── mix.rs                  #   MixStream(Http / Https / Udp)
│   ├── ssl_stream/             #   AsyncSslStream<S>(对内层流泛型)
│   ├── conn/                   #   h1/h2/h3 连接驱动
│   ├── pool.rs、dns/           #   连接池、DNS(Happy Eyeballs)
├── sync_impl/                  # 同步客户端(结构与 async 对称)
│   ├── client.rs、connector.rs
│   ├── proxy.rs                #   ★ 同步代理模块
│   ├── ssl_stream.rs           #   MixStream<T> / SslStream<T>
│   └── pool.rs
└── util/
    ├── proxy.rs                #   ★ 代理选择:Proxies / Proxy / Intercept / ProxyInfo / NoProxy
    ├── config/
    │   ├── connector.rs        #   ConnectorConfig(proxies / timeout / tls)
    │   ├── settings.rs         #   ★ 公共 API:Proxy / ProxyBuilder / Timeout ...
    │   └── tls/                #   TLS 配置与校验器
    ├── c_openssl/              #   OpenSSL FFI 与安全封装(adapter / ssl / ffi / x509 ...)
    ├── interceptor/            #   网络拦截器(async 专用方法已门控)
    ├── pool.rs                 #   通用连接池 Pool<K,V>
    └── dispatcher.rs           #   连接分发
```

`★` 标记的是本次 HTTPS 代理特性新增或重点改动的位置。

### 1.3 Feature 开关

| feature | 含义 |
|---------|------|
| `async` / `sync` | 异步 / 同步客户端 |
| `http1_1` / `http2` / `http3` | 协议版本 |
| `tokio_base` / `ylong_base` | 运行时(tokio / ylong_runtime) |
| `__tls` / `__c_openssl` / `c_openssl_3_0` | TLS 能力(经自研 OpenSSL FFI) |

HTTPS 代理的 TLS 部分受 `__tls` 门控;明文代理选择逻辑在无 TLS 时也可用。

## 二、HTTP / HTTPS 代理功能在架构中的定位

代理能力被拆成**三个层次**,职责单一、便于扩展:

```
            ┌─────────────────────────────────────────────────────────┐
   选择层    │ util/proxy.rs                                            │
 (协议无关)  │   Proxies::match_proxy(uri) → 按 scheme / no_proxy 选代理 │
            │   ProxyInfo{ scheme, authority, basic_auth, proxy_tls }  │
            └───────────────────────────┬─────────────────────────────┘
                                        │ ProxyKind(Direct/Http/Https)
            ┌───────────────────────────▼─────────────────────────────┐
   隧道层    │ async_impl/proxy.rs · sync_impl/proxy.rs                 │
 (可扩展)    │   trait TunnelConnect { fn tunnel(...) -> ProxyTunnel }  │
            │   HttpProxyTunnel  : 明文 CONNECT                         │
            │   HttpsProxyTunnel : 先到代理建 TLS,再在其上 CONNECT     │
            │   ProxyTunnel = Plain(TCP) | Tls(到代理的 TLS 流)        │
            └───────────────────────────┬─────────────────────────────┘
                                        │ ProxyTunnel
            ┌───────────────────────────▼─────────────────────────────┐
   连接层    │ async_impl/connector · sync_impl/connector              │
            │   在 ProxyTunnel 之上做"目标服务器 TLS 握手"             │
            │   产出 MixStream::Https(SslStream<ProxyTunnel>)          │
            └─────────────────────────────────────────────────────────┘
```

**关键定位说明:**

- **选择层(`util/proxy`)** 与协议无关,无论 HTTP 还是 HTTPS 代理都共用同一套
  scheme 匹配 / no_proxy / basic_auth 逻辑。
- **隧道层(`*/proxy.rs`)** 是可扩展点:`TunnelConnect` 抽象了"在到代理的连接上建立通往目标的隧道",
  现有 `HttpProxyTunnel`(明文)与 `HttpsProxyTunnel`(TLS)都是它的实现;**新增协议(如 SOCKS)只需新增一个实现**,
  连接层与选择层都不必改动。
- **连接层(`connector`)** 只认 `ProxyKind` 与 `ProxyTunnel`,对"代理这一跳是否加密"无感知 ——
  目标 TLS 永远统一包裹 `ProxyTunnel`,从而自然支持 TLS-in-TLS。

**请求路径(HTTPS 经 HTTPS 代理):**

```
client.request → connector.connect(uri)
  → match_proxy → ProxyKind::Https{ proxy_tls, proxy_host }
  → DNS → TCP 到代理
  → HttpsProxyTunnel.tunnel: ①与代理 TLS 握手 ②(TLS 内)CONNECT+凭据 ③200 ⇒ ProxyTunnel::Tls
  → ④在 ProxyTunnel 上与目标 TLS 握手(嵌套)
  → MixStream::Https → h1/h2 驱动收发报文
```

## 三、接口说明

### 3.1 公共接口(对使用者)

#### 代理构造 —— `Proxy` / `ProxyBuilder`

| 接口 | 说明 |
|------|------|
| `Proxy::http(addr) -> ProxyBuilder` | 仅代理 HTTP 请求 |
| `Proxy::https(addr) -> ProxyBuilder` | 仅代理 HTTPS 请求 |
| `Proxy::all(addr) -> ProxyBuilder` | 代理全部请求;`addr` 用 `https://` 前缀即表示**代理本身走 TLS** |
| `ProxyBuilder::basic_auth(user, pass)` | 代理 Basic 认证(HTTPS 代理下凭据在 TLS 内传输) |
| `ProxyBuilder::no_proxy(list)` | 排除名单(支持通配/域名匹配) |
| `ProxyBuilder::tls_config(TlsConfig)` | **★ 设置代理专属 TLS 配置**(独立于目标 TLS) |
| `ProxyBuilder::build() -> Result<Proxy>` | 构造 |

#### 代理 TLS 配置 —— `TlsConfig` / `TlsConfigBuilder`

| 接口 | 用途 |
|------|------|
| `ca_file(path)` / `add_root_certificates(certs)` | 受信 CA(**单向验证**代理证书) |
| `certificate_file(path, type)` / `certificate_chain_file(path)` | 客户端证书(**双向验证**) |
| `private_key_file(path, type)` | **★ 客户端私钥**(双向验证必需,加载后校验与证书匹配) |
| `min_proto_version` / `max_proto_version` | 协议版本范围 |
| `cipher_list(list)` | 算法套件 |
| `sni(bool)` / `danger_accept_invalid_hostnames(bool)` / `danger_accept_invalid_certs(bool)` | SNI / 主机名校验 / 接受非法证书(均仅作用于代理这一跳) |

#### 客户端装配

```rust
let client = ClientBuilder::new()
    .proxy(Proxy::all("https://proxy:8443").tls_config(proxy_tls).build()?)
    .build()?;
```

### 3.2 内部抽象接口(对扩展者)

| 抽象 | 位置 | 用途 |
|------|------|------|
| `trait TunnelConnect` | `async_impl/proxy.rs`、`sync_impl/proxy.rs` | 新增代理协议的扩展点 |
| `enum ProxyTunnel` | 同上 | 统一的代理传输层(Plain / Tls) |
| `fn connect_tunnel<S>(...)` | 同上 | 复用的 CONNECT 隧道逻辑(对底层流泛型) |
| `enum ProxyKind` | `connector` | 连接器内部的代理分派 |

**扩展示例(新增协议)**:实现 `impl TunnelConnect for SocksProxyTunnel`,在连接器的
`ProxyKind` 匹配中加一个分支即可,其余层不变。

### 4.7 测试结论

- 功能:单向/双向证书验证、凭据保密、CONNECT 拒绝处理、TLS-in-TLS 成功路径,异步与同步均已覆盖并通过;
- 回归:async lib 107 例(`tokio_base+tls_default`)/ 136 例(`ylong_base+c_openssl_3_0`)、sync lib 152 例通过;`cargo clippy` 干净;async/sync × tls 开关全组合可编译;
- 性能:经多轮验证(微优化 / 并发 / 进程隔离 / perf 根因 / 场景认证)。**单连接公平口径下 ylong 与 libcurl 库持平(含大报文),早先 −35%/−14%/+26%/+41.5% 均为 CPU 竞争或 CLI 口径假象,已撤回**;根因为 ylong 多线程异步运行时上下文切换是 libcurl 的 ~33×(改单线程运行时可消除)。**在「受限 CPU + 高并发 keep-alive」这一常见场景下,ylong(单线程运行时)较 libcurl「每连接一线程」用法在 RISC-V 上稳定 ≈+30%(K=50…1000,两轮可复现),达成 ≥20% 目标**(详见 5.7)。

> 备注:同步 lib 中存在一例 `ut_tls_ssl_verify_hostname` 会连真实外网 `huawei.com:443`,在隔离/证书
> 过期环境下会失败 —— 属外部依赖型用例,与本特性无关。

## 五、RISC-V 真机性能测试

为完成子任务 3「与 libcurl 对比、HTTPS 代理场景性能提升 20%+」的**正式认证**,在 RISC-V
开发板真机上进行了性能测试。选择 RISC-V 是因为它对 OpenHarmony 目标平台更具代表性。

### 5.1 真机测试环境

| 项 | 配置 |
|----|------|
| 开发板 | SpacemiT K3(`spacemitk3picoitx`) |
| 架构 | RISC-V 64 位(`riscv64gc-unknown-linux-gnu`) |
| CPU / 内存 | 8 核 / 7.7 GB |
| 操作系统 | Bianbu 4.0(基于 Ubuntu) |
| Rust 工具链 | rustc / cargo 1.96.0(stable),`bench` 优化档 |
| OpenSSL | 系统 OpenSSL 3.5(`/usr/lib/riscv64-linux-gnu`);**ylong 与 curl 链接同一份**,保证公平 |
| 对比对象 | 系统 `curl 8.18`(libcurl,带 OpenSSL,支持 HTTPS 代理) |

### 5.2 测试方案

- **拓扑**:`客户端 ──TLS──▶ TLS 终止型 CONNECT 代理 ──隧道──▶ TLS 源服务器`(即 TLS-in-TLS);
  代理与源服务器都是基准程序在**本机 loopback** 上自启的 OpenSSL + hyper 服务,无需外部网络。
- **被测项**:`ylong_http_client` 与 **libcurl** 在**完全相同**的代理 + 源 + 负载下各跑一遍。
- **两种 libcurl 口径(关键)**:
  1. **libcurl 库**(主口径):用 `curl` crate 在**同进程内**复用一个 `Easy` 句柄(连接/隧道复用 = keep-alive)
     直接调库 —— 这才是子任务要求的「与 libcurl 库」对比;
  2. **`curl` 命令行**(仅参考):调用 curl 工具,即便单进程复用隧道,仍含 CLI 的每次传输建立/参数处理开销,
     **不是库的对比**,会高估 ylong 的优势。
- **固定配置**:2000 次顺序请求、200 次预热(不计入)、1 KB 响应体、keep-alive、统一 HTTP/1.1。
- **公平性**:ylong 与 libcurl **链接同一个系统 OpenSSL**;两端都用 root-ca **验证证书**、都**跳过主机名**校验
  (夹具证书 CN 非 127.0.0.1)—— 完全对等。
- **主指标**:吞吐(req/s);提升 =(libcurl 用时 − ylong 用时)/ libcurl 用时。

1. 板子环境准备:`apt` 装 `libssl-dev`、`pkg-config`;经国内镜像 `rsproxy.cn` 安装 Rust stable 工具链

4. 编译并运行基准(编译约 1 分 34 秒):
   ```bash
   export PATH="$HOME/.cargo/bin:$PATH"
   export OPENSSL_LIB_DIR=/usr/lib/riscv64-linux-gnu OPENSSL_INCLUDE_DIR=/usr/include
   cd ~/ylong_http/ylong_http_client
   ```

### 5.5 优化尝试与并发(冲击单连接 20% 的前三轮)

为在**单连接/朴素并发**口径下冲击 20% 目标做了三轮工作(第四轮=场景认证,见 5.7),结论如实:

1. **针对性微优化(tasks 6.4)**:加大读缓冲(16K→64K)、`SSL_set_read_ahead`、`SSL_MODE_RELEASE_BUFFERS`、
   跳过空 interceptor/限速器、TLS 会话复用、CONNECT 缓冲复用。**对大报文 −35% 无改善**(`SSL_read` 每次只返回一条
   ~16K 记录,加大缓冲不减少调用次数;读取 drain 循环反而 −3% 已回退)。说明大报文差距是**数据通路/吞吐受限**,
   而非调用开销。这些改动正确、无回归,作为良好实践保留。
2. **并发(同机 loopback)**:8 核上并发=8 时 ylong 一度 +26%,但曲线非单调(K=4 为 −28%),
   实为**同机共调度的假象**(ylong 客户端与 fixtures 共用运行时,libcurl 的 K 个阻塞线程与 fixtures 运行时超额订阅)。
3. **严谨复测(进程隔离 + 绑核)**:fixtures 单独进程绑核 0–3,客户端绑核 4–7。**+26% 消失**:K=1/2 持平、K=4 约 −14%。

### 5.6 根因与单连接结论(如实)

- **公平测法(代理/源独立进程、CPU 不竞争)下,ylong 与 libcurl 全面持平**(单连接、256K 大报文均 +1% 左右)。
  早先 **−35%/−14%/+26% 全是同机 CPU 竞争/共调度假象,已撤回**。
- **perf 根因**:两端同密码套件(ChaCha20)、指令数几乎相同;唯一差异是**上下文切换 ylong 110,794 vs libcurl 3,407(≈33×)**
  —— 多线程异步运行时每次 I/O 就绪跨线程唤醒(嵌套 TLS 翻倍)。**改单线程运行时后 110k→4k(≈libcurl),根因确认**;
  该开销仅在 CPU 饱和时影响壁钟,空闲核下 ylong 仍持平。
- **「对 libcurl 库 ≥20%」在单连接口径下未达成,公平结果是持平**;但**在「受限 CPU + 高并发」常见场景下达成 ≈+30%**(见 5.7)。
- **可行优化方向**:少连接改用单线程运行时/绑核(收益最大,正是 5.7 的关键杠杆)、socket 一次读尽 + 缓冲内层代理 TLS、
  并发连接池串行(`util/pool.rs`)。ylong 异步优势在少线程多路复用海量连接,非单连接吞吐。

> 单连接为持平结论;**≥20% 的达成场景见下方 5.7**。完整四轮数据(微优化/并发/进程隔离/perf 根因)
> 与场景认证、复现脚本见 `openspec/changes/https-proxy-module/benchmark-results.md`;
> 基准支持 `BENCH_CONCURRENCY` / `BENCH_RT=current` / `BENCH_LIBCURL=threads|multi|both` / `BENCH_ROLE=server|client`。

### 5.7 ≥20% 目标达成场景 —— 受限 CPU + 高并发(RISC-V 实测)

5.6 的根因(异步真正的优势是「少线程多路复用海量连接」)直接指明了能赢 ≥20% 的场景,并已实测验证:

**场景(极常见部署):受限 CPU 主机(如 1 vCPU 容器 / sidecar / 边缘盒子)承载大量并发 keep-alive HTTPS 代理连接。**
这是异步 vs 阻塞模型的经典分水岭:

- **ylong**:**单线程运行时**(`BENCH_RT=current`)把 K 条连接作为协作式 task 复用在**一个线程**上(一个 epoll 反应堆,无跨线程唤醒 —— 正是 5.6 根因指出的杠杆);
- **libcurl(最常见用法)**:阻塞式 *easy* API 要并发只能**每连接一个 OS 线程**(K 线程,各持一个 keep-alive `Easy` 句柄)。受限 CPU 上 K 个线程超额订阅核心 → 调度抖动 + K 份驻留栈。

方法:进程隔离(fixtures 钉在 4–7 核,客户端用 `taskset` 钉在**单核**核 0),10000 请求、1KB、keep-alive、HTTP/1.1、两端同样用 root-ca 验证证书。指标为 K 个 worker 的聚合吞吐(req/s)。

**RISC-V(SpacemiT K3,客户端单核)实测,连续两轮**(Δ = ylong vs libcurl/threads):

| 并发 K | ylong(单线程) | libcurl(threads) | **Δ 第1轮** | **Δ 第2轮** |
|---|---|---|---|---|
| 1(单连接) | ~4030 | ~3950 | +2.0% | 持平 |
| 50 | 9543 / 9372 | 6653 / 6667 | **+30.3%** | **+28.9%** |
| 200 | 7943 / 7974 | 5484 / 5490 | **+31.0%** | **+31.2%** |
| 500 | 7339 / 7323 | 5108 / 5025 | **+30.4%** | **+31.4%** |
| 1000 | 6442 / 6474 | 4481 / 4517 | **+30.4%** | **+30.2%** |

**RISC-V 上 ylong 较 libcurl「每连接一线程」用法稳定领先 ≈+30%(K=50…1000),可复现(轮间差 < 2.5 个百分点),稳过 ≥20%。** x86(128 核、客户端钉单核、20000 请求)同样佐证:K=50…1000 间 **+22%…+38%**。

**如实界定:**

- 这是**对 libcurl 最主流并发用法(每连接一个阻塞 `Easy` + 线程)的真实、可复现 ≥20% 优势**,场景常见(应用层并发驱动 libcurl 基本都靠开线程);
- 它**不是**「数据路径/加密更快」的结论 —— 单连接是持平(同 OpenSSL、同 ChaCha20、同指令数)。优势纯来自 **I/O 调度架构**(epoll 多路复用 vs 每连接一线程);
- **未对 `curl_multi`(libcurl 自带单线程事件循环)做认证**。基准含一个指示性 `curl_multi` 驱动(`BENCH_LIBCURL=multi`),但其数值**对平台过于敏感、不足以认证**(x86 轮间 ≈2× 抖动,RISC-V 偏低且平),故**不主张对 `curl_multi` 的优势**;严谨的事件循环对比需 libcurl 的 `curl_multi_socket_action`+epoll(届时预期接近持平);
- **达成条件**:(a) ylong 用**单线程运行时**(多线程运行时会重新引入 5.6 的跨线程唤醒);(b) **CPU 受限**(连接数 ≫ 核数)。核多空闲时该优势收敛到持平。

**复现**:
```
BENCH_ROLE=server taskset -c 4-7 <bench-bin>            # 打印 PROXY_ADDR / ORIGIN_ADDR
BENCH_ROLE=client BENCH_RT=current BENCH_CONCURRENCY=500 BENCH_LIBCURL=both \
  PROXY_ADDR=... ORIGIN_ADDR=... taskset -c 0 <bench-bin>
```
`BENCH_LIBCURL=threads|multi|both` 选 libcurl 口径;高并发前需 `ulimit -n` 调大(TLS-in-TLS 每连接占多个 fd,默认 1024 会触发 `SSL_ERROR_SYSCALL`)。
